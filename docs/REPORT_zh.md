# AI 寫的 PR 合併後 7 天內被修正或撤回？三種量法，不要混在一起

**先講最顯眼的一條：** 公開工具在 3 個開源 repo 中，被判為 AI 代理撰寫的 81 張 PR，**0 張**留下 revert 或指名修正痕跡（95% 上界 4.5%）。樣本小、判定靠啟發式，這不代表 AI PR 比較安全。

下面三組數字**定義各不相同，不可互相比較或合併**：

| | 對象 | 怎麼判 | 數字 |
|---|---|---|---|
| A. 內部審計 | 作者自己 11 個 repo（agent 開發環境）2,018 張 PR | 模型分類＋第二個模型複核的「假完成」（非人工逐件確認） | 確認下限 6.6%，推估 7–10% |
| B. 公開工具 | 3 個開源 repo 的合併 PR | 零模型、決定性訊號的「留痕訊號率」 | 0.9%–2.4% |
| C. 外部研究 | MSR 2026 研究的 agentic PR | 含 reverting commit | 2.66% |

## A. 內部審計（陽性經第二個模型複核；在此定義下可稱確認下限，但不是人工逐件確認）

盤點 2026-08-01 到 10-16 合併的 2,018 張 PR：合併後 7 天內，有沒有後續 PR 指名在修正它。

- **確認下限 133/2,018 = 6.6%**（Wilson 95% 區間 5.6–7.8%）；原稽核推估真實值 7–10%。
- **分母含未滿 7 天的 PR（右設限）。** 排除最後兩段較新的期間後為 112/1,615 = 6.9%（5.8–8.3%），結論不變。
- **誰抓到的：** 真實使用／實驗 54、獨立審查（多為 AI 審查者）27、不明 26、上線／接線稽核 10、CI 9、擁有者 5、其他 2；**核心驗證閘門 0**。
- **治理強度：** 資料無法顯示更嚴的合併治理會降低假完成率（8 月 7.0%、9 月 6.9%；各層級區間重疊；完全沒設必要檢查的 repo 為 13.1%，但只有 61 張）。
- **方法：** 先用關鍵字篩出後續 PR，由模型初標一次，陽性再複核一次；每件只有一個初標者。限制：漏掉沒留字的默默修正；單張的歸因有雜訊，比例比個案可靠。

來源：〈Repo family false completions, 8/1–10/16〉（作者內部研究筆記，2026-10-17）。

## B. 公開工具：留痕訊號率（不是下限）

`pr-regret`（Apache-2.0、標準庫、不用模型）只看三種痕跡：revert、後續 PR／commit 指名修正、同檔再改。2026-10-23 對公開 repo 的結果：

| repo | 合併 PR | revert | 指名修正 | revert 或指名修正（95% 區間） |
|---|---|---|---|---|
| dotnet/aspire（2026-08） | 333 | 3 | 5 | 8＝2.4%（1.2–4.7%） |
| dotnet/aspnetcore（2026-08） | 308 | 0 | 3 | 3＝1.0%（0.3–2.8%） |
| OpenHands/OpenHands（2026-09-01～15） | 112 | 0 | 1 | 1＝0.9%（0.2–4.9%） |

「同檔再改」為弱訊號（41–79%，忙碌 repo 常改同一批檔案），另列、不併入。

**為什麼不能稱下限：** 漏的方向（默默修正、只引用 issue 的修正、7 天後才發現）與多報的方向（關鍵字誤中）同時存在。我們在另一個時間窗（2026-06）抽 22 件命中，由獨立標註者判讀：15 件確為修正或撤回（精確率 68%，Wilson 95% 區間 47–84%），5 件不是，2 件不明；召回率未量。因此 B 只是「可重現的留痕訊號」，不是真實率。

## C. 外部研究

MSR 2026 Mining Challenge 的〈When AI Code Doesn't Stick: An Empirical Study on Reverted Changes Introduced by AI Coding Agents〉報告 2.66%（以含 reverting commit 計）；其定義與 A、B 不同，不可直接比較（我們未能取得全文，只引用摘要層級的數字）。來源頁：https://2026.msrconf.org/details/msr-2026-mining-challenge/27/

## 怎麼解讀

1. A 是陽性經第二個模型複核的下限（非人工確認），B 是啟發式訊號，C 是另一種定義；三者不互相驗證。
2. 為什麼只有真實使用與審查抓得到：合併閘門檢查合併當下的條件，而這類缺陷多半等到有人實際使用或讀程式才現形（A 中 54 件靠使用、27 件靠審查，核心閘門 0）。更多合併前關卡對此類失敗的證據支持有限；較有證據的方向是讓「完成」等到真實使用的見證。
3. 其他限制：B 只看 3 個 repo、1–2 個月；AI 撰寫的判定是啟發式（作者帳號、分支前綴、內文標記）；公開 repo 與我們的環境不同。
