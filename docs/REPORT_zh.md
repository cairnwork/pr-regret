# AI 寫的 PR 合併後 7 天內被修正或撤回，比例多少？

**一句話結論：約 7–10%（作者自己的 11 個 repo 實測），而且能在合併時擋下它們的自動閘門幾乎是零；抓得到的主要是真實使用和人工審查。**

## 1. 我們自己的數字

作者在 11 個 repo 的 agent 開發環境裡，盤點 2026-08-01 到 10-16 合併的 2,018 張 PR，問一個問題：合併後 7 天內，有沒有後續 PR 指名在修正它或把它撤回。

- **確認下限 133/2,018 = 6.6%**（Wilson 95% 區間 5.6–7.8%）；推估真實值 7–10%。主 repo 6.9%，其他 10 個 repo 6.2%。
- **治理鬆緊與假完成率沒有關係**：8 月 7.0%，9 月在最嚴的合併治理下 6.9%；各 repo 的比例也不隨治理強度單調變化，區間重疊。
- **誰抓到的**：真實使用 54 件、獨立人工審查 27 件、上線／接線稽核 10 件；自動閘門幾乎 0（核心驗證閘門 0 件、CI 9 件）。
- **日常追蹤**：同一指標每天算，約 6.0–6.2%；單張精確率與召回率各約 0.73，只看週比例。

來源：〈Repo family false completions, 8/1–10/16〉（作者內部研究筆記，2026-10-17）；〈7 天內被修正／退回比例指標與事故評測集〉（內部研究筆記，2026-10-19）。

**方法與公開版的差別。** 內部版先用關鍵字篩出可疑的後續 PR，再用模型分類「這張後續 PR 是否在修正前一張」，陽性再由第二個模型複核。公開版（本工具）**完全不用模型**，只用決定性訊號：revert 指向、被指名修正、同檔再改。所以公開版更可重現、也更保守；兩者數字不可直接相比。內部版的限制：漏掉沒留字的默默修正、每件一個標註者、最後兩段期間尚未滿 7 天。

## 2. 外部對照

MSR 2026 Mining Challenge 的研究〈When AI Code Doesn't Stick: An Empirical Study on Reverted Changes Introduced by AI Coding Agents〉（Oukay、Begoug、Chouchen、Ouni）在 33,580 張 AI 代理 PR（AIDev 資料集：Claude、Copilot、Cursor、Devin、OpenAI Codex）中，量到 **2.66% 含至少一個 reverting commit**；分代理看，OpenAI Codex 0.7%、GitHub Copilot 7.6%。來源頁：https://2026.msrconf.org/details/msr-2026-mining-challenge/27/ 。

**定義不同，不能直接比。** 它只量 revert；我們量 revert 加指名修正。它的 revert 判定方式與有無時間窗，我們沒讀到論文方法章節：**待查證**（arXiv 版本也待查證）。因此 2.66% 與下方的 revert 欄只能當同一量級的參考。

## 3. 公開工具在開源 repo 上量到的下限

我們用 `pr-regret`（Apache-2.0、只用標準庫）對三個有明顯 AI 代理 PR 的公開 repo 各跑一個月（OpenHands 半個月），2026-10-23 執行：

| repo | 合併 PR | revert | 指名修正 | revert 或指名修正（95% 區間） |
|---|---|---|---|---|
| dotnet/aspire（8 月） | 316 | 3 | 21 | 24＝7.6%（5.2–11.1%） |
| dotnet/aspnetcore（8 月） | 295 | 0 | 4 | 4＝1.4%（0.5–3.4%） |
| OpenHands/OpenHands（9/1–9/15） | 110 | 0 | 2 | 2＝1.8%（0.5–6.4%） |

只看被判為代理撰寫的 PR：78 張（5＋13＋60）**零件**留下痕跡，95% 上界 4.7%。樣本太小，這不代表代理 PR 比較安全，只代表沒找到決定性痕跡。「同檔再改」是弱訊號（40–79%，忙碌 repo 常改同一批檔案），分開報、不併入比例。人工抽看 10 件指名修正命中，4 件確為修正、2 件模糊、4 件不是，之後已加規則排除 backport、發版分支與清單式 PR（詳見 `docs/VALIDATION.md`）。

## 4. 怎麼解讀

1. **全部是下限。** 只抓得到留下痕跡的：標題、描述、commit 訊息、檔案清單。默默修正、引用 issue 而非 PR 的修正、7 天後才發現的問題都看不到。這不是真實的假完成率。
2. **同一量級，但不能跨 repo 比。** 作者的 6.6% 下限、公開 repo 的 1.4–7.6%、外部研究的 2.66% revert，落在同一個個位數百分比附近；但 repo、期間、定義都不同。
3. **為什麼只有真實使用與審查抓得到。** 合併閘門檢查的是合併當下的條件（測試、規則、簽章），而這類缺陷多半要等到真的有人用、或有人讀程式才現形：我們的 133 件裡 54 件靠真實使用、27 件靠人工審查，自動閘門約 0，且加嚴治理沒有讓比例下降。給 agent 加更多合併前關卡，對這類失敗的成本效益有限；較有證據支持的方向是讓「完成」要等真實使用的見證。
